NL2SQL 演进路径

NL2SQL 不是一步到位的技术，而是经历了四代演进。Agentic BI 是第四阶段——在 Agent 基础上加入语义治理、安全护栏和执行控制。

Phase 1
Prompt-only
直接让大模型生成 SQL

Phase 3

Agentic BI

SQL 正确 + 口径一致 + 安全可审计 + 可解释 + 自愈

语义化 表、列、指标、关系都有机器可读的业务描述

可追溯 数据来源、语义资产版本和查询过程可追溯

Anthropic / Claude 实践

分析 Agent 的三类失败

① 概念歧义 — 用户说"活跃用户"时，Agent 不知应绑定哪个指标和时间窗口。
② 数据陈旧 — 指标定义变化后，Agent 仍按旧知识生成答案。
③ 检索失败 — 正确定义存在，但 Agent 没能从庞大搜索空间中可靠找到它。

R/V/G/D 四引擎 RAG 检索

NL2SQL 检索的对象是结构化语义资产，不同问题需要不同检索方式。单一向量检索远远不够。

R
Relation
精确匹配
"GMV 是什么" — 通过关系型数据库精确查找术语绑定和指标定义
V
Vector
语义检索
"和销售相关的表" — 通过 pgvector 向量相似度检索语义相关资产
G
Graph
图遍历
"哪些表可以 Join" — Apache AGE 图数据库遍历表间关联关系
D
Dynamic Few-shot
经验复用
"上次类似问题怎么写" — 动态检索历史成功问答，注入 Prompt
并行 + 串行协作：R、V、D 并行执行降低延迟；G 依赖前面检索得到的资产 ID，因此串行执行。典型流程：R+V+D 并行 → 合并 → G 图遍历 → 构造检索上下文

Part 5

Agent 编排：LangGraph 与状态机

确定性 DAG + 条件路由，结合 Plan-and-Execute、Reflexion 和 ReAct 三种理论，实现"受控自治"。

七类路由策略

路由类型触发场景
标准查询常规 NL→SQL 流程
SQL 缓存命中相似度 ≥ 0.92，跳过 RAG 和生成
元数据查询询问表结构、字段、指标定义
深度分析多步骤洞察、趋势分析
图推理复杂关联、血缘追踪
知识问答业务规则、概念解释
澄清请求歧义或信息不足，主动询问

自愈回路

护栏失败 → 触发自愈流程
分析失败原因 → 反馈具体错误类型
Corrective Retrieval 补充检索
重新生成 SQL → 再次校验
最多重试 2 次，防止无限循环

HITL 人工审批触发条件

DDL 操作 大批量 DELETE/UPDATE 跨租户导出 高成本查询
Anthropic / Claude 实践

Skills：语义资产之外的补充层

语义资产回答"数据是什么、在哪里、怎么算"；Skills 回答"应该咨询哪些来源、按什么顺序分析、有哪些常见陷阱"。 Knowledge Skills 引导 Agent 在多个候选表之间选择正确对象； Runbook Skills 复用留存、漏斗、异常和队列分析等分析方法。 关键业务指标口径必须由业务与数据团队人工编排，不能完全依赖 LLM 自动生成。

Part 6

五层 SQL 护栏与执行安全

SQL 是大模型生成的，不代表可以直接信任。生成层、输入层、数据库执行层三重防护缺一不可。

L1 语法校验 SQL 是否能够正确解析 直接拒绝
L2 策略黑名单 禁止 DROP、DELETE、TRUNCATE 等危险操作 直接拒绝
L3 AST 列白名单 引用的列必须在语义资产中存在 进入自愈
L4 术语语义校验 SQL 是否遵守指标和业务术语定义 进入自愈
L5 成本估算 EXPLAIN 判断扫描量和执行成本是否超限 进入自愈
核心原则：AI 的权限不应该超过用户的权限。即使大模型生成了缺少过滤条件的 SQL，数据库层的 RLS 也应继续限制最终结果。执行层保留：强制 LIMIT、查询超时、PII 脱敏 UDF、RLS 行级安全、CLS 列级安全。
Part 7

记忆系统与工具使用

四层记忆按生命周期分离，触发式写入保证可审计性，SQL 语义缓存保持数据新鲜。

⚡
Working Memory
会话级 · 结束后清除
当前对话和查询上下文。承载本次查询的所有中间状态，会话结束后自动清除。
👤
Profile Memory
用户级 · 跨会话持久化
用户偏好、常用指标、权限配置。跨会话保存，个性化查询体验的基础。
📖
Episodic Memory
平台级 · 经验复用
历史问题和 SQL，成为 Dynamic Few-shot 的来源。需经 Admin 审核才能进入检索池。
🔧
Correction Memory
平台级 · 错误防护
用户纠正过的错误和错误模式，用于避免 Agent 重复犯同类错误。
SQL 语义缓存策略：缓存 SQL 而非查询结果；相似度 ≥ 0.92 命中缓存后仍重新执行 SQL；TTL 约 15 分钟。这样可以保持数据新鲜，避免返回过期数据。

核心结论

五条最重要的判断

从十个专题中提炼出的关键认知，指向企业级 Agentic BI 的本质。

1
数据平台建设的下一道门槛是 AI 可消费性
有数据不等于业务能查询；有 Schema 不等于 AI 理解业务口径。AI-Ready 是新的基础设施门槛。
2
Agentic BI 的核心不是大模型，而是工程治理
语义平面、多路 RAG、SQL 护栏、权限控制、自愈与审计——大模型只是其中一个组件，工程治理才是决定质量上限的因素。
3
语义资产是 AI 数据平台的核心基础设施
表、列、指标、术语、规则和 Join 关系都需要版本化管理。业务知识必须从人的经验中沉淀为机器可读资产。
4
结构化数据需要通过语义化和治理变得可被 Agent 消费
分析 Agent 负责查询，语义资产统一口径，Skills 沉淀可复用分析知识，SQL 护栏与权限体系控制执行风险——四者缺一不可。
5
企业级 Agent 的关键是"受控自治"
简单任务可以自动化，复杂任务需要规划和评估，高风险操作必须人工审批。所有查询都需要可观测、可追溯、可解释。
Data + AI 转型不是把一个大模型接到数据仓库上，
而是把已有数据平台进一步语义化、治理化、工具化，
使数据能够被 Agent 正确理解、安全调用，
并在真实业务反馈中持续进化。
