时代命题：从 Data Platform 到 AI-Ready Data Platform

★ Agentic BI 真正要解决的问题

不是"聊天机器人能不能生成 SQL"，而是：SQL 是否正确、业务口径是否一致、查询是否安全、结果是否可解释、出错后是否能够修复。五件事缺一不可。

Build vs Buy：为什么在高合规场景常常选择自建
路线优势代价

选择自建通常基于三个原因：金融行业需要较深的术语、监管合规、脱敏和权限治理；当时 AWS China 对部分云 AI 产品支持有限；需要完全控制 SQL 生成和审计过程。

【Anthropic 实践】分析 Agent 的三类失败 · 数据不是软件

概念与实体歧义——用户说"活跃用户"或"收入"时，Agent 不知道该绑定哪个指标、字段、数据集和时间窗口。数据陈旧——指标定义、Schema 或业务规则变化后，Agent 仍按旧知识作答。检索失败——正确的定义已经存在，但 Agent 没能从庞大的搜索空间中可靠地找到它。

代码 Agent 面对的往往是开放式问题、有多个可接受实现；数据分析 Agent 面对的通常是固定事实问题，只有一个正确的数据源和口径——映射错一次，就会生成一条语法完全正确、结果却完全错误的 SQL。Anthropic 的实践显示，约 95% 的商业分析查询可以被 Claude 自动化处理，整体准确度约为 95%——这组数据属于 Anthropic 的生产实践，不应外推为其他系统的基准。

架构：双平面、五层模型与语义治理
依赖只能向下：治理层约束智能层和数据层，运行时不能反向修改治理资产
1.1 双平面架构 语义 / 数据分离

系统拆成两个平面，各自拥有不同的变更节奏和扩展节奏：

平面职责管理方式
语义平面管理表、列、指标、术语、规则和 Join 关系Git + YAML，离线发布
数据平面执行 SQL 和返回查询结果Redshift Serverless，在线执行
★ 分离带来的好处

改指标口径不需要改执行引擎；更换数据执行后端不需要重写语义治理；语义变更可以走 PR、CI 和审计流程；执行和治理拥有不同的扩展节奏。

1.2 五层逻辑模型与九步查询流程 确定性 DAG
五层逻辑模型 — 依赖只能向下
L1 交互层
对话界面、结果展示、SSE 流式输出
L2 编排层
状态机、路由和流程控制
L3 智能层
RAG、Agent 编排、SQL 生成、护栏
L4 数据层
SQL 执行和数据存储
L5 治理层
语义资产、术语、指标和业务规则——只能被依赖，不能被运行时反向修改
九步查询流程
① 用户自然语言提问
② Supervisor 接收请求并加入治理上下文
③ Query Understanding 识别意图和实体
④ 根据意图进行确定性路由
⑤ R/V/G/D 四引擎检索
⑥ 规划 Join 路径
⑦ 在语义约束下生成 SQL
⑧ 经过五层 SQL 护栏和自愈流程
⑨ 执行 SQL 并进行可视化

早期 POC 只有"提问、生成 SQL、执行、返回"四步，后来因为出现错误 Join、幻觉列和危险 SQL，逐渐增加检索、规划、校验和自愈环节。

★ 确定性 DAG，而不是完全自主的 ReAct

企业级场景需要路径可预测、过程可审计、问题可排查、权限和风险可控制。代价是灵活性低于纯 ReAct，但更适合金融等高合规场景。

【Anthropic 实践】规范数据集与制品共存

为每个核心业务概念确定单一可信的数据集和指标定义，为数据集指定清晰的 Owner，主动弃用近似复制品；物理汇总表和缓存可以存在，但应机械地从规范模型推导，而不是另立一套事实。数据建模代码、语义层、参考文档、规范仪表板定义和相关 Skills 尽量放在同一仓库中——Schema 或转换逻辑变化时，相关文档和分析方法应在同一个 PR 中同步更新，CI 需要检查跨层引用和文档漂移。

2.1 R / V / G / D 四引擎 RAG 检索 检索不是单一向量搜索

NL2SQL 检索的对象不是普通文档，而是结构化语义资产。不同问题需要不同检索方式：

★ 术语绑定是系统级硬约束，不是"大模型自己判断"

术语绑定贯穿整个流水线：Reranker 中提高绑定资产权重 → Prompt 中注入术语约束 → SQL 生成时强制使用绑定指标 → 护栏检查术语与 SQL 是否一致 → 失败后 Corrective Retrieval 优先检索正确资产。

Corrective-RAG 与 Token 预算

检索质量分为高（直接使用）、中（重排后使用）、低（扩大检索范围、改写问题或补充检索）三档。当前实现更接近一种简化的 CRAG：很多情况下是在 SQL 生成或护栏失败之后，才触发补充检索。未来应该把检索质量评估前置。

【Anthropic 实践】真实来源的优先级

Agent 不应把所有上下文等权处理：①语义层和编译后的指标定义（权威映射）②转换血缘（指标如何从源表到达最终数据集）③蒸馏后的历史查询模式（提炼成结构化文档或 Few-shot）④业务上下文（流程、政策、特殊情况）。Anthropic 的实验显示，直接把数千条原始历史 SQL 提供给 Agent，准确率提升不足 1%；经过整理的结构化文档则更有效——历史查询适合被"蒸馏"，不适合不加整理地作为主要指导来源。

2.2 Agent 编排：LangGraph 与状态机 受控自治

LangGraph 的核心组成是 State（中间状态）、Node（具体任务）、Edge（流转规则）、Checkpointer（执行检查点）和 Store（长期记忆）。主链路：

Supervisor→ Query Understanding→ Router→ RAG→ Planner→ SQL Generator→ Guardrail→ Executor→ Visualization
七类路由（由确定性意图映射表控制，而非大模型自由决定）
路由类型说明
标准查询常规 NL → SQL 主流程
SQL 缓存命中相似度 ≥ 0.92 时跳过 RAG 和 SQL 生成，直接复用历史 SQL，但仍需经过护栏和执行
元数据查询询问表结构、字段、指标定义
深度分析多步骤洞察、趋势分析
图推理复杂关联、血缘追踪
知识问答业务规则、概念解释
澄清请求信息不足时主动询问
自愈回路（最多重试两次）
护栏失败
分析失败原因，反馈具体错误
Corrective Retrieval 补充检索
重新生成 SQL，再次校验（≤2 次）

不同错误采用不同修复方法：语法错误返回解析错误，列不存在时重新检索列名，成本过高时调整 Join 或过滤，术语不一致时重新绑定指标和规则。

HITL 人工审批与模型分配

以下高风险操作需要人工介入（LangGraph 通过 interrupt 暂停流程，审批通过后再恢复执行）：

DDL 大批量 DELETE/UPDATE 跨租户数据导出 高成本查询

不同任务使用不同模型：Query Understanding 使用快速模型，SQL 生成使用推理能力更强的模型，Insight 使用长文本生成模型。同时支持模型故障切换、Admin 在线覆盖和 Circuit Breaker。

★ 三种 Agent 理论的结合，形成"受控自治"

Plan-and-Execute 对应多步骤任务编排和确定性 DAG；Reflexion 对应失败后的自愈；ReAct 对应受控的条件路由。最终形成的不是完全自由的自治 Agent。

⚠️ 本章指出的不足

Supervisor 过轻；路由缺乏自学习；全局 State 字段过多，存在"上帝对象"问题；SQL 执行前的 HITL 覆盖仍不够充分。

【Anthropic 实践】Skills：语义资产之外的补充层

语义资产回答"数据是什么、在哪里、怎么算"，Skills 回答"应该咨询哪些来源、按什么顺序分析、有哪些常见陷阱"。Knowledge Skills 是概念到实体的薄路由器，用于在多个候选表、列和指标中选择正确对象；Runbook Skills 是分析过程编码器，复用留存、漏斗、异常、趋势和队列分析等方法。关键业务指标和分析口径应由业务与数据团队人工编排，不能完全依赖 LLM 自动生成——自动生成的定义可能重新引入本来要消除的歧义。

提示注入防御与咨询模式

输入层需要防止用户通过恶意指令诱导大模型：输入模式检测、System Prompt 与用户内容分离、禁止泄露系统提示词、禁止用户身份升级、Agent 以用户身份执行。对于复杂或高风险查询，系统不直接执行，而是先展示 SQL 和解释，等待用户确认后再执行。

⚠️ 简单关键词检测无法解决所有间接提示注入

必须采用纵深防御，而不是把提示注入防御当成一次性的过滤规则。

执行层：数据库级硬防线
强制 LIMIT 查询超时 PII 分级暴露 RLS 行级安全 CLS 列级安全 脱敏 UDF 独立 Redshift Serverless 实例
★ 核心原则

AI 的权限不应该超过用户的权限。即使大模型生成了缺少过滤条件的 SQL，数据库层的 RLS 也应该继续限制最终结果。

不同查询路由有不同的记忆预算：简单 KPI 查询注入较少历史信息，复杂分析则可以使用更多历史经验。

工程判断 · 触发式记忆而非自由决定

系统不让大模型自由决定"记住什么"，而是由明确事件触发：查询成功、用户反馈、用户澄清或 Admin 审核。这种方式更容易审计，但可能遗漏用户没有明确表达出来的隐性偏好。

SQL 语义缓存与动态 Few-shot

系统选择缓存 SQL，而不是缓存查询结果：相似度达到 0.92 可以命中，命中后仍重新执行 SQL，TTL 约 15 分钟——保持数据新鲜，避免返回过期数据。

成功问答不能直接进入 Few-shot 库，而要经过审核流程：

记录为 pending_review→ Admin 审核→ approved→ 满足相似度 / 置信度 / 失败次数条件后参与检索

这是为了避免错误 SQL 污染后续生成。

当前代码解释器沙箱只有较弱的进程内隔离，生产环境仍需要升级到进程或容器级隔离。

2.5 数据平面与 CDP 整合 增量能力，不是另起炉灶

Agentic BI 不应直接把 AI 查询打到生产数仓，而应建立独立的数据平面：dev、qa、prod 分别用于开发、验收和正式使用，避免大模型生成的复杂 SQL 影响生产 BI。生产环境用 Redshift Serverless，开发环境用 pg_mooncake，通过统一执行器和 SQL 方言转换在本地低成本开发、再切换到云端执行。

⚠️ 本地通过不等于生产通过

Redshift 和 PostgreSQL 的方言差异需要通过双方言 CI 校验。

PG Supernode：一个 PostgreSQL 实例承载四类检索
组件承载内容
R关系型检索
Vpgvector 向量检索
GApache AGE 图检索
D动态 Few-shot
CacheSQL 语义缓存

好处是运维简单、事务一致性好、开发联调成本低；代价是规模和专用性能有限，未来可切换到 Qdrant、Milvus 等专用向量数据库。

★ 与 CDP 整合：不另建一套独立数据体系

复用数据湖到数仓的数据同步、复用 Gold 层数据、继承 RLS/CLS 和脱敏规则、延伸多租户角色、通过独立实例执行 AI 查询——Agentic BI 是在现有 CDP 数据平台上增加 AI 消费层，而不是另起炉灶。

AI-Ready 数据供应四步
① 识别 AI 消费场景→ ② 为核心表编写语义资产→ ③ 经过 CI 校验并发布→ ④ 根据实际使用反馈持续迭代

最大成本是语义资产的人工编写和业务确认。可以让大模型从 Schema 自动生成 YAML 草稿，但必须经过人工审核后才能发布。未来可通过 Iceberg 或 Delta 让数据湖也具备表语义、Schema 演化、事务和时间旅行能力，使湖和仓共用一套语义层。

收尾：评估、演进与核心结论
上线不是终点，只有评估、追踪、反馈和成本闭环才能持续演进
3.1 三种评估方式与三级评估体系
端到端评估
最接近用户体验，但难以定位错误环节
轨迹评估
有助于排查每一步问题，但成本较高
结果评估
SQL 和数据是否正确，客观可量化，但不能全面反映过程质量
评估层级内容
运行时评估分别评估检索结果、SQL 结果和最终答案，主要在深度分析路由中启用
治理 CI 评估发布前检查引用完整性、术语到指标绑定、规则是否可计算、Few-shot SQL 是否有效、是否存在循环依赖或悬空引用
LLM-as-a-Judge从正确性、可解释性、安全性和效率四个维度评价，只能作为规模化评估工具，仍需人工抽检

RAG 重点关注 DeepEval / Ragas 四个指标：faithfulness（答案是否忠于上下文）、answer_relevancy（是否真正回答问题）、context_precision（召回内容是否相关）、context_recall（是否召回全部必要内容）。

指标数值

★ 如果只能优先推进一件事
Roadmap 中排在最前面的是 P0 · 多租户 RLS——在受控自治的框架下，行级权限是所有其他能力的地基，没有它，语义治理和护栏再完善也管不住"看见谁的数据"这条最基本的红线。
3.4 能力边界：覆盖约 90% 高频分析查询，而不是万能分析师
边界 1
跨库关联外部数据
现状需要人工或规则兜底，Agent 尚不擅长自动打通
边界 2
复杂窗口函数
现状生成正确率明显低于常规聚合查询
边界 3
金融产品材料和费率政策等非结构化推理
现状超出结构化语义资产的覆盖范围
边界 4
最近几分钟的实时流查询
现状当前架构面向秒级到近实时，非严格流式
边界 5
10 张以上表的超复杂查询
现状Join 路径规划和护栏成本随表数量快速上升
边界 6
多层子查询和高度复杂的分析逻辑
现状建议转交 Runbook Skill 或人工分析
【Anthropic 实践】验证与防止知识腐烂 · 分阶段实施路线

固定快照离线评估——在固定数据、Schema 和语义资产快照上运行测试查询，保证测试可重复。按 PR 消融测试——修改语义层、Skill、Prompt、规范数据集或路由/检索/护栏逻辑的每个 PR，都应通过临时移除组件或对比变更前后结果来确认收益与退化。在线对抗性审查——对真实生产查询做边界和反例检查，并展示数据源、更新时间和 Owner；可提升约 6% 的准确度，但会增加约 32% 的 Token 使用和约 72% 的延迟，更适合复杂分析或抽样查询，而不是所有简单查询的默认路径。

分阶段实施：数据基础（1–2 周）→ 语义层（2–3 周）→ Skills（3–4 周）→ 验证（1–2 周）→ 持续迭代。

核心结论
1
数据平台建设的下一道门槛是 AI 可消费性
有数据不等于业务能查询；有 Schema 不等于 AI 理解业务口径。
2
Agentic BI 的核心不是大模型，而是工程治理
语义平面、多路 RAG、SQL 护栏、权限控制、自愈与审计——工程治理决定了大模型能力的可用边界。
3
语义资产是 AI 数据平台的核心基础设施
表、列、指标、术语、规则和 Join 关系都需要版本化管理；业务知识必须从文档和人的经验中沉淀为机器可读资产。
4
结构化数据需要通过语义化和治理变得可被 Agent 消费
数据分析 Agent 负责数仓查询，语义资产统一业务口径，Skills 沉淀可复用的分析知识和流程，SQL 护栏与权限体系控制执行风险。
5
★ 企业级 Agent 的关键是"受控自治"
简单任务可以自动化，复杂任务需要规划和评估，高风险操作必须人工审批；所有查询都需要可观测、可追溯、可解释。
Data + AI 转型不是把一个大模型接到数据仓库上，而是把已有数据平台进一步语义化、治理化、工具化，使数据能够被 Agent 正确理解、安全调用，并在真实业务反馈中持续进化。
